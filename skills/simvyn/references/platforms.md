# Platform support and limits

These limits describe Simvyn's current implementation, not everything the underlying operating systems might support through other tools. Check the installed CLI's help and actual target before choosing commands.

## Host and device prerequisites

| Host or device       | Requirements and interpretation                                                                                                                                                                                                                                                                     |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| macOS host           | Node.js 22 (22.14.0+) or 24+. Full Xcode with the selected developer directory and installed simulator runtimes for iOS; Android SDK tools for Android.                                                                                                                                             |
| Linux host           | Node.js 22 (22.14.0+) or 24+ and Android SDK tools. iOS adapters are unavailable.                                                                                                                                                                                                                   |
| Windows host         | Not a supported Simvyn host; do not infer support from Node.js availability.                                                                                                                                                                                                                        |
| iOS simulator        | Must exist in Xcode's available runtimes. Most commands require it to be booted. Simulator ID is a UUID.                                                                                                                                                                                            |
| Physical iPhone/iPad | Uses `xcrun devicectl` (Xcode 15+ baseline). Simvyn IDs begin with `physical:`; retain that prefix. Unlock, pairing, trust, Developer Mode, signing, and toolchain/device OS compatibility can affect operations. Discovery labels these devices `booted`; it does not prove every action is ready. |
| Android emulator     | `adb` and `emulator` available on PATH, configured AVD/system image. Shutdown ID `avd:<name>` becomes `emulator-<port>` after boot.                                                                                                                                                                 |
| Physical Android     | USB debugging and host authorization, visible to `adb`. Offline/unauthorized devices are filtered out of Simvyn discovery. ID is the ADB serial.                                                                                                                                                    |

Useful read-only prerequisite checks are `node --version`, `xcode-select -p`, `xcrun simctl list devices`, `xcrun devicectl list devices`, `adb version`, `adb devices -l`, and `emulator -list-avds`, chosen for the relevant platform. Use the dashboard's tool diagnostics for its existing environment report; there is no `simvyn doctor` command.

Device lifecycle creation, clone, rename, erase, delete are iOS simulator operations. Android AVDs can be discovered, booted, and stopped; creation/deletion is not exposed by this CLI. Physical devices cannot be treated as disposable simulators. Android physical shutdown is currently a no-op, and iOS physical shutdown is rejected.

## Non-obvious limitations

**Build artifacts must match the target.** A device `.ipa` is not automatically a simulator build. The simulator install path can extract an IPA, but cannot make an incompatible architecture/platform binary run. Use a simulator `.app` or an explicitly compatible archive for a simulator; use a properly signed physical-device build for an iPhone. Android install expects an APK; AAB conversion and split-APK installation workflows are not exposed.

**Physical iOS has a narrower CLI than dashboard/API claims may suggest.** The `fs` CLI resolves iOS containers through `simctl get_app_container`; `logs` uses `simctl spawn`. Neither becomes a devicectl equivalent simply because the ID is physical. Prefer supported app lifecycle operations; report an unsupported request instead of dropping the prefix or substituting another target silently.

**App data inspection is not arbitrary phone access.** Android files and databases use `run-as <package>`, requiring a debuggable installed app; a release build may be uninspectable. iOS simulator paths refer to the host-accessible app container. Query results are human-readable. CLI SQLite handles are read-only; editing shown in the dashboard is a separate workflow.

**Live Android SQLite snapshots may be incomplete.** The CLI query path copies the main database file, without explicitly copying its `-wal` and `-shm` siblings. A missing row is not proof the app did not write it. If current transactional state matters, use an app-supported export/checkpoint or an appropriately captured consistent snapshot; terminating an app alone does not prove WAL was checkpointed.

**Android clipboard fallback changes behavior.** `clipboard set` tries the clipboard service, then falls back to input text in the focused field, truncating to 256 characters. It is not a guarantee of clipboard contents. `clipboard get` is unavailable. Avoid treating this as a reliable cross-platform clipboard round trip or using it to inject secrets into an unknown focused field.

**Settings can persist and disrupt sessions.** iOS locale writes require a device reboot. Android locale uses `su` and restarts zygote; Play Store/release system images may not allow it. Display density/size, font scale, orientation, battery state, and TalkBack should be restored to the user's previous values or agreed defaults after temporary tests. `display ... --reset` restores hardware defaults, which may differ from preexisting overrides. Appearance/status-bar changes are not connectivity or real battery simulation.

**Permissions use platform-specific names.** iOS examples include `camera` and `photos`; Android names include `android.permission.CAMERA` (the `android.permission.` prefix is added if omitted). The app/OS must support granting that permission through the platform command. The CLI does not expose a permission capability schema; check the installed platform help or target app manifest when uncertain.

**Content sizes are names, not arbitrary scales.** Typical values are `extra-small`, `small`, `medium`, `large`, `extra-large`, `extra-extra-large`, `extra-extra-extra-large`, and `accessibility-medium` through `accessibility-extra-extra-extra-large`. Android maps these to font scales. These settings support visual checks; they do not perform an accessibility audit or inspect a UI hierarchy.

**iOS crashes are host reports.** The crash reader scans `~/Library/Logs/DiagnosticReports` and `Retired` on the Mac. It is not a physical-device download and is not scoped to the supplied simulator ID. Match process and time to the reproduction before attributing a crash. The CLI summary omits IDs; the dashboard can provide report details for subsequent `--view` use.
